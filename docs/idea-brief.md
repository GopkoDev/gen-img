# Idea brief — Ukiyo

## 1. Raw idea

> хочу зробити міні проект, локал фірст або може лайтвейт десктоп. суть така в мене є опен роутер чи версель гетевей, в проекті я промптом генерую картинку, (варіації це текст ту імг, імг ту імг, ітг і текст ту імг) далі ці картинки відповідно локально зберігаються а наступне це коли я її переглядаю в галереї яку дає нам ui то бачу промпт, модель, ціну, час творення, картинку яку було додано до промпта, короче побільше метадати щоб при потребі можна було відтворити + кастомний якийсь коментар додати. я хочу це зробити за допомогою sdd плагіна як міні проект

## 2. Problem

Зараз картинки генеруються в playground-ах OpenRouter / Vercel AI Gateway (owner-reported). Проблеми (owner-reported):

- картинки й промпти губляться — коли треба зробити щось схоже, нема звідки взяти попередній промпт/результат;
- незручно перейти на іншу модель з тим самим запитом;
- щоб змінити наявну картинку, її треба вручну завантажити, знову приєднати до промпта і описати зміну.

Бажаний результат: кожна генерація зберігається локально разом із метаданими, достатніми для повтору чи варіації, а наявну картинку можна взяти як вхід для наступної генерації без ручного перезавантаження.

## 3. Users

Один користувач — власник ідеї, на одній машині (owner-reported, рішення). Без авторизації, синхронізації чи спільного доступу. Ключі API провайдерів лежать локально в нього.

## 4. Why now

Конкретного тригера чи дедлайну не встановлено. Мотивація — постійний біль із playground-ами (§2) і бажання пройти міні-проєкт через SDD-пайплайн (owner-reported).

## 5. Out of scope

- Кілька користувачів, акаунти, синхронізація між пристроями — рішення owner-а (лише «я, одна машина»).
- Нативна десктоп-обгортка в першій версії — рішення owner-а: спершу локальний вебзастосунок (сервер на localhost + UI в браузері), десктоп пізніше.
- Пошук і фільтри по галереї — не в першій версії (owner не обрав для MVP), кандидат у roadmap.
- Гарантоване піксельне відтворення — owner прийняв, що «відтворити» = повторно надіслати ті самі входи (§7).

Підтверджені обмеження (owner-required): провайдери — OpenRouter і Vercel AI Gateway, **обидва з першої версії**; режими text→img, img→img, img+text→img; картинки й метадані зберігаються локально.

## 6. Risks

1. **Різнорідність API провайдерів (найслабше місце).** Vercel має два різні механізми (chat completions з `modalities` для мультимодальних LLM vs `/v1/images/generations` + `/v1/images/edits` для image-only моделей), OpenRouter — `/api/v1/images` з `input_references`. Підтримка вхідних картинок, `seed`, `size`/`aspect_ratio`, `n` залежить від моделі. Наслідок: обидва провайдери з першої версії = ≥3 шляхи виклику і нормалізація метаданих; MVP більший, ніж здається. Зворотність: висока (адаптери ізольовані).
2. **Ціна Vercel недоступна одразу.** `total_cost` береться окремим `GET /v1/generation?id=` асинхронно (може бути «Usage event not found» кілька секунд); для BYOK не включає вартість запиту. Наслідок: ціна в записі може бути «pending» і потребує дозапиту.
3. **Відтворюваність не гарантована.** `seed` в OpenRouter «where supported», у Vercel не задокументований.
4. **Дрейф документації.** Назви моделей/ендпоінтів швидко змінюються; висновки нижче актуальні на 2026-10-18.

## 7. Recommendation

Напрям (рішення owner-а): локальний вебзастосунок для одного користувача, що генерує картинки через OpenRouter і Vercel AI Gateway (обидва з v1) у трьох режимах і зберігає кожну генерацію локально — файл картинки + копії вхідних картинок + запис метаданих: провайдер, модель, промпт, параметри (seed/size/aspect/n — що модель прийняла), вхідні картинки, ціна (з позначкою pending, де вона ще не відома), час створення, тривалість, сирий запит/відповідь, коментар, теги.

MVP-дії в галереї (рішення owner-а): перегляд метаданих, коментар, **повторити/змінити модель** (форма, заповнена тими самими входами), **використати як вхід** (img→img в один клік, з посиланням на «батьківську» генерацію), **теги та видалення**.

«Відтворити» = повторно надіслати ті самі входи, не піксельна ідентичність (рішення owner-а, прийнято після fact-check).

Основний trade-off: обидва провайдери з першої версії збільшують MVP (≥3 шляхи виклику, асинхронна ціна Vercel). Розглянута простіша альтернатива — один провайдер спершу — owner відхилив.

Outcome: ready-for-roadmap

Наступна дія: проєкт порожній (greenfield) → `survey` закладає фундамент (стек, структура, зберігання), `scaffold` — скелет, далі `roadmap` розбиває MVP на кроки (напр. сховище+галерея → адаптер OpenRouter → адаптери Vercel → img→img/ланцюжки → теги/видалення).
